Sessions 4–5 delivered volunteer profiles and organization accounts (verified+active public org pages, `/me` internals, `verificationStatus` machine through `StatusTransitionService`). Nothing yet lets an org offer work. This session ships the `opportunities` entity so Session 7 can attach applications. The inventory pins the shape: `opportunities` with embedded `positions` (opportunities module owns both, inventory §1 module 9), §3 indexes, the §5 lifecycle (`draft → published → in_progress → completed`; `published | in_progress → closed | cancelled`), §2.8 routes, §6/§7 decisions 1/4/5/7 (participant activation is job-driven and publisher must be verified+active), and F11's feed-index caveat. Reused infra: `createSchema` (`src/common/schema`), canonical slug pipeline (`slugifyText` + `createWithUniqueSlug`, A12), cursor pagination (`normalizeLimit`/`encodeCursor`/`decodeCursor`), `StatusTransitionService` + `StatusTransitionRegistry`, S1 `JobRegistry`, `PublishGateService` seam, `SettingsService` (`system_settings`), DTO pipes (`whitelist` + `forbidNonWhitelisted`), `@Public()`/`@Roles('organization')`/`@CurrentAccount`, error envelope `{ statusCode, code, message, details? }`. `.env.example` already declares `PUBLISH_GATE_ENABLED` (S0, commented "if true, gate lock blocks publish even before Session 13") — only confirmation is needed. `SettingsService.ensureDefaults()` already seeds `publishGate.maxPendingOpportunities=3` but is not yet invoked at boot.

## Goals / Non-Goals

**Goals:**
- `opportunities` schema (embedded `positions` sub-document, `requiredCount`/`filledCount`/`requiredSkills` as `skillId` refs, `status` enum with the §5 machine, `startDate`, `applicationDeadline`, `location { wilayaId, municipalityId, coordinates }`, unique `slug`, `organizationId`) + the §3 index set.
- Public: `GET /opportunities` (feed, filters, published-only, cursor 20/50), `GET /opportunities/:idOrSlug` (published-only 404), `GET /opportunities/recommended` (empty until S12).
- Org: `POST/GET /organizations/me/opportunities`, `PATCH/DELETE /opportunities/:opportunityId`, `POST /opportunities/:opportunityId/{publish,close,cancel,complete}` through `StatusTransitionService`, and positions CRUD with the `requiredCount >= filledCount` seat rule.
- Publish guard: `verified`+`active` org required (403 `ORG_NOT_VERIFIED`); `PublishGateService#evaluate(org)` consulted (409 `PUBLISH_GATE_LOCKED` when enabled and locked).
- `opportunityStartTicker` job handler (idempotent) registered in the S1 `JobRegistry`; confirmation of `PUBLISH_GATE_ENABLED` in `.env.example`; `ensureDefaults()` invoked at boot so `publishGate.maxPendingOpportunities=3` is seeded.

**Non-Goals:**
- Applications/participations (S7 — including their models, their accept transaction, and per-participant histories; we only touch those collections through raw adapters). Recommendation rules (S12), gate math (S13), `in_progress` notification (S13), admin force-close (S16), media existence checks (S8), `$text`/geo index final choice (F11 decided in S19).

## Decisions

### D1. Schema: embedded positions, §3 index set
`OpportunitySchema` via `createSchema`: top-level `organizationId` (ObjectId), `slug` (unique), `title`, `description`, `categoryId` (ObjectId ref), `status` (enum `draft|published|in_progress|completed|closed|cancelled`, default `draft`), `startDate` (Date, optional), `applicationDeadline` (Date, optional), `location { wilayaId, municipalityId, coordinates: [lng, lat] }`, and `positions: [PositionSchema]` with `title`, `description`, `requiredCount` (≥1), `filledCount` (default 0, ≥0), `requiredSkills: [ObjectId]`. Indexes (inventory §3): unique `slug`, `(status, startDate)`, `(organizationId, status)`, 2dsphere `location.coordinates`, text `title, description`, and `positions.requiredSkills.skillId` (multikey). Rationale: inventory §3 is explicit; the opportunity is an aggregate (positions embedded, like `organizations` level sub-documents) so seat counts update atomically with the doc — no separate collection to join. Positions are validated for `requiredCount >= filledCount` at the DTO/service boundary on every position mutation.

### D2. Feed is indexed facet queries, not `$text` (F11)
`GET /opportunities` builds a `find()` filter on indexed facets and never relies on the text index: `status: 'published'`; optional `location.wilayaId`, `location.municipalityId`, `categoryId`; `startDate` bounds from `from`/`to` (`$gte` / `$lte`); `skillId` via `positions.requiredSkills` equality (multikey index); `hasOpenPositions=true` via `positions: { $elemMatch: { $expr: { $lt: ['$filledCount', '$requiredCount'] } } }`; `q` via a case-insensitive, regex-escaped, length-capped `$or` on `title`/`description` with an early `categoryId` bound when present. Order: `sort({ _id: -1 })` (recency), cursor = last `_id` hex, page with `_id: { $lt: cursor }`; `normalizeLimit` (default 20, max 50). Rationale: a single query cannot use the text index and 2dsphere together, and F11 defers that canonical choice to S19; indexed facets + bounded regex are correct today and stay correct after S19. Alternative rejected: `$text: { $search }` — breaks under the F11 constraint and is not needed for MVP feed quality.

### D3. Detail by id-or-slug, recommended declared first
`GET /opportunities/:idOrSlug`: when the param is 24-hex `Types.ObjectId.isValid` and a `findOne({ _id })` matches, use it; otherwise `findOne({ slug })`. Everything not `status: 'published'` returns 404 (F5) — no owner special-case: the owning org reads its own rows via `GET /organizations/me/opportunities` (all statuses). `GET /opportunities/recommended` (`@Roles('volunteer')`, returns `[]`) is declared before `:idOrSlug` in `OpportunitiesController` so Express never binds `recommended` to the catch-all. Rationale: F5 + the §2.8 "owner via me" contract; the `:slug` shadow trap from §2.7 applies equally here.

### D4. `/organizations/me/opportunities` cross-module route ordering
The org-internals routes are authored in this module's controller with the static path `organizations/me/opportunities`, but S5's `OrganizationsController` already registers `GET organizations/:slug/opportunities`. Express binds in registration order, so a param route registered first would swallow `me`. This module is therefore imported **before** `OrganizationsModule` in `AppModule` (purely additive import), guaranteeing `me/opportunities` registers first; an e2e asserts `GET organization/me/opportunities` hits the opportunities handler (returns the org's list) and not `:slug/opportunities`. Rationale: keeps all opportunity routes in one module/controller (inventory ownership) without editing S5 files. Alternative rejected: adding the routes into `OrganizationsController` — cross-module coupling and edits to another session's file.

### D5. Lifecycle through `StatusTransitionService`; `accepted → active` registered on the `opportunity` entity
`OpportunitiesModule.onModuleInit` registers the `opportunity` whitelist in `StatusTransitionRegistry`: `draft→published`, `published→in_progress`, `in_progress→completed`, `published→closed`, `published→cancelled`, `in_progress→closed`, `in_progress→cancelled`, and the job path `accepted→active` (roadmap §4 S6: "the full opportunities machine; `accepted → active` (job)"). Field mutation stays in this module: each route calls `statusTransitions.assert({ entityType: 'opportunity', entityId, from, to, actor })` first, then `$set` the new status (the service intentionally does not mutate — S1 contract). This writes `status_histories`. The job asserts `published→in_progress` per opportunity and its participant activation is validated against the registered `accepted→active` pair. S7 registers the full `task_participants` machine separately and owns per-participant histories for withdraw/remove; the shared pair is additive (`register` merges).

### D6. Publish guard: verified+active, then the gate seam
`POST /opportunities/:opportunityId/publish` resolves the owning org by `organizations.userId` (S5 `OrganizationsService.findByUserId`, imported via `OrganizationsModule`). If `verificationStatus !== 'verified' || status !== 'active'` → 403 `ORG_NOT_VERIFIED` (SO §7 decision 7 / §6). Otherwise `await publishGate.evaluate({ id: org._id })`; a `.locked` result → 409 `PUBLISH_GATE_LOCKED`. Only then assert `draft→published` and flip status. The inert default returns unlocked unless `PUBLISH_GATE_ENABLED=true` (A7); S13 swaps the real counter via DI without touching this route. `PUBLISH_GATE_ENABLED` already exists in `.env.example` (S0) — confirmed, not re-added. `SettingsService.ensureDefaults()` is invoked from `OpportunitiesModule.onModuleInit` (inject the S1 global `SettingsService`) so `publishGate.maxPendingOpportunities=3` is seeded at boot without editing S1 files.

### D7. Pre-S7 adapters for `task_participants` and `applications`
S7 owns both collections, but this session's job must activate participants and the guards need "no accepted participants" / "no applications". A small `src/opportunities/task-participants.adapter.ts` wraps the raw driver connection (`this.connection.db.collection(...)`):
- `activateAcceptedForOpportunity(opportunityId)`: `updateMany({ opportunityId, status: 'accepted' }, { $set: { status: 'active' } })` — idempotent (second run matches nothing).
- `countAccepted(opportunityId)`: `countDocuments({ opportunityId, status: { $in: ['accepted', 'active'] } })` — used by the post-publish PATCH/position guards; returns 0 when the collection does not exist yet.
- `countByPosition(positionId)`: `countDocuments({ positionId })` — used by position DELETE ("only if no applications", §2.8).
Field names follow inventory §3 (`task_participants`: `opportunityId`, `positionId`, `status`; `applications`: `positionId`). A comment marks the adapter as S6-only and S7 replaces it with the owning Mongoose models. Rationale: keeps the job and guard semantics real without violating "each collection has exactly one owning module" (the model is S7's; we only touch the driver collection where the roadmap requires). Alternative rejected: defining a `task_participants`/`applications` model here — ownership violation the roadmap is strict about.

### D8. Job handler with a system actor
`opportunityStartTicker` registered in `JobRegistry.register('opportunityStartTicker', ...)` at `onModuleInit`: find `{ status: 'published', startDate: { $lte: now } }` (`(status, startDate)` index); for each: assert `published→in_progress` (actor = a fixed zero sentinel `new Types.ObjectId('000000000000000000000000')` standing for the system, valid for the ObjectId cast in `StatusTransitionService`), `$set` status to `in_progress`, then `adapter.activateAcceptedForOpportunity(id)` and `eventEmitter.emit(DomainEvents.OpportunityStarted, { opportunity })` after the writes. Idempotency: after the first run the status is `in_progress` so the second run withdraws nothing; `accepted` participants are matched exactly once. `startDate` unset → not matched, skipped.

### D9. PATCH/delete and positions CRUD rules
- `PATCH /opportunities/:opportunityId` (owning org only, 404 otherwise): before publish — title, description, categoryId, startDate, applicationDeadline, location editable; after publish — only `description` and a forward-only `applicationDeadline`, and only while `adapter.countAccepted == 0`; when accepted participants exist the PATCH is rejected. `slug`, `organizationId`, `status`, `positions` are never settable from the body (DTO `forbidNonWhitelisted`).
- `DELETE /opportunities/:opportunityId`: hard-delete only when `status === 'draft'` (the §0 hard-delete exception), else 409 `OPPORTUNITY_NOT_DRAFT`.
- Positions CRUD (owning org): `POST .../positions` adds a position (draft free; published only while `countAccepted == 0`); `PATCH .../positions/:positionId` edits and rejects `requiredCount < filledCount` (409 `POSITION_REQUIRED_COUNT_LOWER_THAN_FILLED`); `DELETE .../positions/:positionId` rejects if `filledCount > 0` OR `adapter.countByPosition > 0` ("only if no applications", §2.8).

## Risks / Trade-offs

- [Cross-module route order relies on `AppModule` import order] → Mitigation: e2e regression asserts `me/opportunities` wins over `:slug/opportunities`; the D4 comment documents the invariant for S7+.
- [Raw-driver writes on `task_participants`/`applications` could drift from S7's real schema] → Mitigation: only the two documented field shapes are used (drawn verbatim from inventory §3), the adapter is isolated in one file with an S7-swap comment, and S7 owns all future reads/writes.
- [`accepted → active` registered under `opportunity` overlaps with S7's `task_participants` machine] → Mitigation: `register` is additive (Set merge) and the pair is identical in both machines; S7 replaces the adapter with its models and per-participant histories while the job behavior stays.
- [Text + 2dsphere mutual exclusivity (F11)] → Mitigation: feed avoids `$text`; the §3 text index still exists for future use; S19 records the canonical choice and may drop the text index.
- [Required-skills existence check adds a skills dependency] → Mitigation: `SkillsModule` exports `SkillsService`; create/patch validate `requiredSkills` against active skills with a 400 `SKILL_NOT_FOUND` otherwise. Cheap and bounded.
- [Slug collisions / slug from Arabic title] → Mitigation: the canonical `createWithUniqueSlug` pipeline (A12) already transliterates and retries on E11000.

## Migration Plan

No data migration: one new collection (`opportunities`) created by the app on boot; `task_participants`/`applications` collections are merely read/updated via the driver adapter and do not require models. `system_settings.publishGate.maxPendingOpportunities` is upserted by `ensureDefaults()` at boot (idempotent). Rollback = revert this session's commit; S7 depends on the collection and the whitelist but the roadmap ordering is strict. No new runtime packages; `.env.example` unchanged (`PUBLISH_GATE_ENABLED` present since S0 — confirmed). Parallel-merge: `AppModule` gains one additive import line; no S4/S5 file is modified.
