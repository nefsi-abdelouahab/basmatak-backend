## Context

The core loop is open at the reporting stage. S7's accept transaction seeds a `task_participants` row with `{ opportunityId, positionId, applicationId, organizationId, volunteerId, status }` and the embedded `position` sub-document in `opportunities` carries the task's `title`/`description`. S8's media module owns `MediaOwnership` (global `@Injectable`), which exposes `assertFor(mediaId, actorId, purpose)` — existence, ownership (404 `MEDIA_NOT_FOUND` for absent/foreign), and purpose (409 `MEDIA_PURPOSE_MISMATCH`) — with `submission_evidence` already an allowed `MediaPurpose`. S9's `NotificationsEventHandlers` already forwards-registers `submission.submitted` (reads `payload.submission.organizationId` → notifies the org account), so this session only emits. The S1 `StatusTransitionRegistry.register(entityType, pairs)` pattern is proven by S6 (`opportunity`) and S7 (`task_participant`) module `onModuleInit` hooks; `StatusTransitionService.assert` validates + writes `status_histories`.

There is no `submissions` collection, no module, and none of the eight §2.12 routes. Media metadata lives in `media` rows (`type: file|l link`, `mimeType`, `confirmedAt`, `deletedAt`); videos are `type=link` (host allowlist), images/pdfs are `type=file`. Those media rows are what the consent rule and the "evidence per deliverable" rule read.

Constraints carried into this design: NestJS 10 + TS strict, Mongo ObjectId ids, `/api/v1` prefix, `{ statusCode, code, message, details? }` errors with UPPER_SNAKE codes, cursor pagination (default 20 / max 50) via `common/pagination/*`, class-validator whitelist + forbidNonWhitelisted, and the §6 rule that the only entity a caller may not read is treated as not-found (404 for foreign ownership). One session = one OpenSpec change; this change is shared with Part B, so the whitelist carries the full machine now and Part B only writes `approved|rejected`.

Part B context: S9's `NotificationsEventHandlers` also forward-registers `submission.verified` and `submission.rejected` (both notify the volunteer via `notifySubmissionVolunteer`, dedupe-keyed on the payload's `submission` ref). The S1 `StatusTransitionService.assert` accepts an optional `session` so histories write inside a Mongo transaction (proven by the S7 accept/withdraw flows, which mirror the shape Part B's verify uses: `@InjectConnection`, `startSession`, `session.withTransaction`, in-txn status histories via `assert(..., { session })`, in-txn notification writes via `NotificationsService.createInSession` → `NOTIFICATIONS_REPOSITORY.createInSession`, post-commit emit). `volunteer_profiles.stats` exists with `completedTasks`/`verifiedExperiences`/`volunteerHours` (default `0`); `task_participants` has `completed` in its enum and the whitelist registers `accepted → active → completed`; media rows carry `purpose` incl. `submission_evidence` and `visibility` `public | private`. Verification code generation uses the built-in Node `crypto` (A12), and `common/slug/slugify.util.ts` already provides the `isDuplicateKeyError`/E11000 retry pattern to reuse for code-collision retries.

## Goals / Non-Goals

**Goals:**
- A `submissions` module (`backend/src/submissions/`) with a `submissions` collection: `participantId` (unique — one submission per participation, reused on resubmission), denormalized `volunteerId`/`opportunityId`/`positionId`/`organizationId`, `deliverables` (position-derived descriptor snapshots), `description`, `consentConfirmed` (Boolean, default `false`), `evidence` (array of `{ mediaId }`), `status` (`draft` default), S1 base options and the §3 indexes `(opportunityId, status)` + `(volunteerId, status)`.
- The eight §2.12 routes: create (409 on second), patch (draft edits; rejected→draft), submit (draft→submitted with description + evidence-per-deliverable + consent rule), `me`, detail (owner/org, includes media metadata), org inbox (`?status=&opportunityId=`), and `start-review` (submitted→under_review).
- `submission` whitelist registered at bootstrap (full machine, so Part B needs no re-registration) and `submission.submitted` emitted after each successful submit exactly once via the S1 EventEmitter bus.
- E2E in `backend/test/submissions.e2e-spec.ts` plus unit coverage for submit validation and the rejected→draft round-trip.

**Non-Goals:**
- Part B (this same change): verify/reject routes, the `verifications` collection, `volunteer_experiences`, the `Review` model, and volunteer stats are **in scope** — see the Part B design decisions below.
- Out of scope for both parts: portfolio (P2/S13), the P2 review controllers/reliability (S13), public profile publishing of experiences (S12 reads them), and media access beyond the exposure rules (§6, A6).
- Changing S9's already-registered handler or adding a new notification handler; changing S7/S8 module code beyond reading their models.
- Any new package, env var, or route beyond the routes in the proposal; no changes to `opportunities`/`applications`/`participations` collections beyond reads.

## Decisions

**D1 — Module layout.** New `backend/src/submissions/`:
- `schemas/submission.schema.ts` — `SubmissionsCollection = 'submissions'`, `SUBMISSION_STATUSES = ['draft','submitted','under_review','approved','rejected']`, fields per the spec, `evidence: [{ mediaId: ObjectId }]`, `deliverables: [{ title, description }]`, `consentConfirmed` default `false`, `status` default `draft`, `createSchema` base options (timestamps, `versionKey:false`, ObjectId→string `toJSON`). Indexes: unique `participantId`, `(opportunityId, status)`, `(volunteerId, status)`.
- `submissions.service.ts` — `createForParticipation`, `updateDraft`, `submit`, `listMine`, `getDetail`, `listForOrganization`, `startReview`; the only file that calls `MediaOwnership`, `StatusTransitionService`, and `EventEmitter2`.
- `submissions.controller.ts` + `dto/submission.dto.ts` — the eight routes, `Auth` guards, role guards: volunteer routes use the volunteer role (create/patch/submit/me/detail) and org routes use the organization role (inbox/start-review/detail). All callers come from the JWT `sub`.
- `submissions.module.ts` — `MongooseModule.forFeature` for `SubmissionsCollection`, re-registers `OpportunitiesCollection` + `TaskParticipantsCollection` (precedent: notifications module re-registers foreign models for read-only lookup), and implements `OnModuleInit` registering the `submission` whitelist.

**D2 — Create derives the draft from the participant + its position.** `POST /participations/:participationId/submissions`: load the `task_participants` row by `_id` scoped to caller `volunteerId` (absent/foreign → 404, matching S7's `requireOwned*` pattern), then load the opportunity and its embedded `positions` sub-document by `participantId` → `positionId`. `deliverables` is a snapshot `[{ title, description }]` copied from that position sub-document — a descriptor-per-position array so the evidence-per-deliverable rule is checkable against a stable, immutable snapshot even if the org later edits the opportunity. `volunteerId`/`opportunityId`/`positionId`/`organizationId` come from the participant row (denormalized so the inbox/detail/notification never need joins). Insert competes against the unique `participantId` index; a duplicate surfaces `E11000` → `409 SUBMISSION_ALREADY_EXISTS`. Alternative considered — letting the volunteer author `deliverables` freely — rejected: the inventory pins deliverables to the position's expected outputs and a free-typed list would let volunteers change the contract on resubmission.

**D3 — Edit semantics (rejected→draft, one record, unlimited resubmission).** `PATCH /submissions/:submissionId` accepts `{ description?, evidence?, consentConfirmed? }`. Owner check first (foreign → 404). If `status === 'rejected'`, transition `rejected → draft` via `StatusTransitionService.assert` and then apply the edit; if `status === 'draft'`, apply directly; any other status (`submitted`/`under_review`/`approved`) → 409 `INVALID_STATUS_TRANSITION`. Every evidence `mediaId` in the incoming array is validated through `MediaOwnership.assertFor(mediaId, volunteerId, 'submission_evidence')` before the update is written, so the whole patch is atomic as a single `findOneAndUpdate` after validation (no partial state). This mirrors the §5 machine (`rejected → draft → submitted again`, unlimited) and decision 2 / roadmap; the same record is always reused.

**D4 — Submit is validate-first, then transition, then emit.** `POST /submissions/:submissionId/submit`: owner check (404 for foreign). Validation order, each a `400` business error with no transition written:
1. `description` is non-empty.
2. Every `deliverables` entry is covered by at least one `evidence` mediaId (allow one evidence to satisfy exactly one descriptor — matching the inventory's "at least one evidence per deliverable"). No evidence at all → 400 `EVIDENCE_REQUIRED`; any unevidenced descriptor → 400 `EVIDENCE_REQUIRED`.
3. Any evidence media whose row is `type=link` (video) or `type=file` with an `image/*` mimeType requires `consentConfirmed === true` (decision 6). Missing → 400 `CONSENT_REQUIRED`. PDF-only evidence never triggers the rule.
   The media rows are fetched via `MediaOwnership.assertFor` per evidence id (this doubles as the existence/ownership/purpose gate on submit, matching the patch path).
Then `StatusTransitionService.assert({ entityType:'submission', entityId, from:'draft', to:'submitted', actor })` writes the history, the row is updated to `submitted`, and only after both succeed `this.events.emit(DomainEvents.SubmissionSubmitted, { submission: updated })` — payload shape matching S9's handler (`payload.submission.organizationId`). The E2E routes list the emitted payload through the injected `EventEmitter2` (precedent S9 §5.1).

**D5 — Registration timing and full-machine whitelist.** `SubmissionsModule.onModuleInit` calls `registry.register('submission', [['draft','submitted'],['submitted','under_review'],['under_review','approved'],['under_review','rejected'],['rejected','draft']])` — identical to the S6/S7 pattern. The whitelist intentionally carries `approved|rejected` now so Part B's verify/reject transactions only call `assert` and never touch registration; this session implements no `approved|rejected` write path. `StatusTransitionService.assert` rejects anything unlisted (`INVALID_STATUS_TRANSITION`, 409) and writes nothing.

**D6 — Detail and inbox resolve ownership without joins.** `GET /submissions/:submissionId` loads the row and returns it with evidence media metadata; access: caller's `volunteerId` matches the row, or an org account whose own organization (`organizations.userId → organizations._id`) equals the row's `organizationId`. Otherwise 404 (non-owner read = not-found, §6). The org inbox `GET /organizations/me/submissions` resolves the org id from the JWT account once, then queries `{ organizationId, ...(status), ...(opportunityId) }` with the §3 `(opportunityId, status)` index; foreign org rows are structurally unreachable. Volunteer calling the inbox → 403.

**D7 — Cursor pagination reuses the S1 helpers.** `me` and inbox use the existing `common/pagination/*` encode/decode with `limit` default 20 / max 50, newest-first (`_id` descending), cursor on `_id`. The DTOs are class-validator whitelist + forbidNonWhitelisted.

**D8 — Automatic start-review on inbox open is optional, so the explicit route is the contract.** `POST /submissions/:submissionId/start-review` is implemented unconditionally (owning org → 404 for others; any non-`submitted` status → 409 `INVALID_STATUS_TRANSITION`; else `submitted → under_review` through `assert`). Auto-start on first inbox open is left to the frontend to invoke (the road map lists it as "may be implicit"); because `under_review` is in the whitelist, a repeated auto-start call is idempotent (already-`under_review` → assert's `INVALID_STATUS_TRANSITION` would fire, so the service treats `under_review` target state as success — no second history row). Decision: keep the service semantics "transition TO under_review" and treat an already-`under_review` row as a no-op success for the implicit path.

## Part B — Verify, reject, verifications, experiences, reviews

These decisions extend the same change. Part A registered the full machine so Part B only writes `approved|rejected`; every transition goes through `StatusTransitionService.assert` with an optional `session`.

**D9 — Verify is a multi-document transaction that mirrors the S7 accept flow.** `VerificationService.verify(account, submissionId, dto)` opens `@InjectConnection().startSession()`, then `session.withTransaction`:
1. Re-read the submission (owner org check first: caller's own org `organizations.userId → organizations._id` must equal `submission.organizationId`, else 404).
2. Precondition: submission.status must be `submitted` or `under_review`, else `409 INVALID_STATUS_TRANSITION`. To keep `assert`'s from/to exact, when status is `submitted` the transaction first asserts `submitted → under_review`, then `under_review → approved` (both whitelisted); when already `under_review`, a single `under_review → approved` gives one history row.
3. Participant (`task_participants` by `submission.participantId`) → `completed` via assert with `session` (whitelisted `accepted|active → completed`).
4. Insert `verifications` (status `verified`, `notes`, `decidedAt`, `decidedBy` = account.sub) with `session`.
5. Insert `volunteer_experiences` with `session` — snapshots title/description/skills/duration from the opportunity's position sub-document (resolve by `opportunityId` + `positionId`), `evidenceIds` from `submission.evidence[].mediaId`, generated `verificationCode`, `publicVisibility` default `public`.
6. If `dto.review` was provided, insert a `reviews` row (rating + optional comment) with `session` — the unique `submissionId` index enforces one-per-submission; an E11000 here → `409 REVIEW_ALREADY_EXISTS`.
7. `$inc` `volunteer_profiles.stats` (`completedTasks`, `verifiedExperiences`, `volunteerHours`) by `(1, 1, duration)` via `{ userId: submission.volunteerId }`.
8. Assert submission `submitted → under_review → approved` (writes both history rows) and write the volunteer notification in-txn via `NotificationsService.createInSession` (recipient `submission.volunteerId`, type `submission.verified`, payload `{ submissionId }` — matching the S9 handler's dedupe key so the post-commit handler is swallowed, F4).
After commit, emit `submission.verified` (`{ submission: updated }`). Any throw rolls back everything — no verification, no experience, no review, no stats change, submission intact.

**D10 — Verify accepts an already-`submitted` submission without requiring a prior start-review call.** The precondition is `submitted|under_review` so the org can decide straight from the inbox (the roadmap's E2E "under_review-already-reviewed" and "resubmits can't double-verify" both resolve via the 409 guard). This makes `start-review` optional in practice while keeping the whitelist canonical.

**D11 — Rejection retains the reason on the `verifications` `rejected` row, not inside `status_histories`.** The ROADMAP says "reason retained in `status_histories`", but the `status_histories` schema is `{ entityType, entityId, from, to, actor }` — it has no free-text column (confirmed in ``status-histories.schema.ts``, and modifying it touches the core S1 model and its spec). The inventory's real requirement (§5) is that "every rejection and its reason is kept" for the volunteer. Decision (deviation, reported): `submission.rejected` payload and the `verifications.reason` field carry the reason; `status_histories` gets the usual `(from,to)` row. `reject()` is **non-transactional** (per the roadmap): assert `submitted|under_review → rejected` (traversing `submitted → under_review` first when needed), update submission row, insert `verifications` (`rejected`, reason), emit `submission.rejected`. `reason` is required (400 when absent).

**D12 — `verifications` are created terminal (`verified`/`rejected`), never `pending`.** F12 removes the unreachable `pending → verified|rejected` machine; the models store the decided terminal state directly from the flows. Status enum `['verified','rejected']`; unique `submissionId`; `(organizationId, status)` index per §3.

**D13 — `volunteer_experiences` snapshots the position at verify time.** Title and description are copied from the opportunity's embedded position sub-document (the same source `createForParticipation` reads for `deliverables`); `skills` from the position's `requiredSkills`; `evidenceIds` from the submission. This keeps the public proof stable even if the org later edits the opportunity — same rationale as D2's deliverables snapshot. `publicVisibility` defaults `public` so the S12 public profile can show it unless the volunteer opts out. There is no create/edit route (inventory §2.14). **`duration` gap:** the roadmap/inventory say the experience copies `title/description/skills/duration` and stats increment `volunteerHours = duration`, but no source schema carries a `duration` today — the opportunity position is only `{ title, description, requiredCount, filledCount, requiredSkills }` (confirmed in ``opportunity.schema.ts`` / the S6 DTO). Decision: the experience document carries a `duration` (Number, default `0`) and `volunteerHours` increments by it; with no producer yet the value is `0` for current data. Recorded as an Open Question so a future session can add a duration to positions without a behavior change here.

**D14 — Verification code generation uses built-in `crypto` with the A12 alphabet and E11000 retry.** A helper in the verifications module (or `common/`) generates 8 uppercase chars from base32 excluding `0/O/1/I` using `crypto.randomBytes`/`randomInt`; insert competes against the unique `verificationCode` index; on E11000 (reuse `isDuplicateKeyError` from `common/slug/slugify.util.ts`) it retries with a fresh code for a bounded number of attempts, then throws (rolls back the transaction). Direct reuse of `createWithUniqueSlug` is rejected: it appends a numeric suffix to a base slug, but the code must be uniformly random and unguessable for possession (A6).

**D15 — Reviews: schema/model now, controllers never in this change (F16).** `backend/src/reviews/review.schema.ts` defines `ReviewsCollection`, the `Review` model (`submissionId` unique, `organizationId`, `volunteerId`, `rating`, `comment?`) and indexes; a minimal `reviews.module.ts` makes it injectable in the verifications module. No controllers are exposed (S13 adds `POST /submissions/:submissionId/review`, `GET /volunteers/me/reviews`, `GET /organizations/me/reviews`). The in-transaction write keeps schema ownership clean while enabling the atomic verify.

**D16 — Experience detail and public proof resolve media/identity with the exposure rules.** `GET /experiences/:experienceId`: volunteer owner only (404 otherwise); returns the experience snapshot + evidence media metadata + the review for that `submissionId`. `GET /verify/:verificationCode`: public (guest), resolves by code, 404 unknown; returns the A6 summary with evidence media filtered to `visibility: public` and volunteer handle only — private media never leaves the system on this route, and `publicVisibility` does not gate the possession-based proof.

## Risks / Trade-offs

- **Unique-index-driven 409 depends on catching `E11000`.** If the unique `participantId` index were ever dropped, a second create would silently write a second row. → Schema declares the index; the E2E seeds a duplicate-create case against the running rig, and the service also does an explicit pre-check `findOne({ participantId })` before insert (belt-and-braces; the E11000 catch remains the authoritative race guard).
- **Editing the opportunity after a draft is created no longer re-derives `deliverables`.** That is intentional (stable snapshot for evidence coverage), but an org editing position titles mid-draft could make the snapshot diverge from the current position. → The snapshot is end-user-facing text; the slug/title divergence is cosmetic and Part B's verify notes can reference it. Documented trade-off, not a correctness risk.
- **Emit-after-commit is not transactional with the submit.** A crash between the transition write and the bus emit loses the notification (the row is `submitted`, the org gets no nudge). → Same posture as S7's post-commit conveniences; the row itself is the source of truth and the inbox still lists the submission. Not retried in this session (no queue, per the roadmap's no-queues constraint).
- **Media rows are read (not transactionally updated) for consent/ownership.** A media row deleted between validate and save → the submission references deleted media. → `assertFor` filters `deletedAt: { $exists: false }`; Part B's verify transaction will re-check liveness before approving. Acceptable for MVP.
- **Module ordering in `app.module.ts` must stay additive.** Sibling archives warn against reordering existing imports. → Append `SubmissionsModule` to the imports array; the full build/e2e gate plus the `GET /organizations/me/submissions` (org-owned) vs `GET /participations/:id/submissions` (volunteer) route split have no path collisions with existing controllers.
- **Verify's duplicate-guard interplay: unique `submissionId` on `verifications` AND the status precondition.** A resubmitted-and-re-approved submission reuses the same `submissionId` row (unique `participantId`, decision 2). The verify guard (`submitted|under_review` only) prevents a second full approve of an already-`approved` row; the unique `submissionId` on `verifications`/`volunteer_experiences` prevents a second proof row per submission. → The service must treat a verify hitting an existing `volunteer_experiences`/`verifications` row for that `submissionId` as the already-approved 409 path (precondition check first, so the E11000 is the belt-and-braces guard only).
- **`verificationCode` collision window is tiny but must roll back cleanly.** With 8 chars (~32^8 ≈ 1.1×10^12) collisions are astronomically rare, but under a concurrent rig they are possible. → The E11000 retry loop inside the transaction re-draws a code and retries the insert within the same transaction; bounded attempts then throw, rolling back the whole verify (no partial proof). Unit test forces a collision via stub.
- **Reason-on-`verifications` deviation.** The roadmap's phrase "reason retained in `status_histories`" is satisfied functionally (D11) by the `verifications.reason` field because the S1 `status_histories` model carries no free-text column. → Recorded as a deviation to report; the volunteer always sees the reason via the notification payload and can re-read it from the API.
- **Reject is not a transaction — same envelope as submit.** A crash between the submission-row update and the `submission.rejected` emit loses the nudge (row is `rejected`, volunteer not notified). → Same posture as S7 post-commit conveniences; reject updates the row first, then emits; the notification is best-effort.

## Migration Plan

Part A: new `submissions` collection only. Indexes (unique `participantId`, `(opportunityId, status)`, `(volunteerId, status)`) build on first boot. Rollback: revert the Part A commit; the S9 handler is a no-op until `submission.submitted` is emitted.

Part B: three more new collections — `verifications` (unique `submissionId`, `(organizationId, status)`), `volunteer_experiences` (unique `submissionId`, unique `verificationCode`, `(volunteerId, publicVisibility)`), `reviews` (unique `submissionId`, `organizationId`, `volunteerId`). All build on first boot via `autoIndex` (test rig + local dev), Atlas warm-up like every prior session. `app.module.ts` gets additive imports for `VerificationsModule`, `ExperiencesModule`, `ReviewsModule` (model only) and `SubmissionsModule` (Part A). No existing collection, env var, or route changes; no existing spec's REQUIREMENTS change (only the new capabilities + the `submissions` delta this change already owns). Rollback: revert the Part B commit; nothing else depends on the verifications/experiences/reviews modules yet (S9's `submission.verified|rejected` handlers are no-ops until these events are emitted).

## Open Questions

- **Auto-start UX ownership.** Whether the frontend triggers `start-review` explicitly or the inbox auto-starts on open is a UI decision; the backend supports both (D8). No blocking question.
- **Deliverable descriptor shape.** The snapshot is `[{ title, description }]` per position (D2). If a future session adds a richer `deliverables` structure to positions, this module would read it through the same snapshot seam — noted for Part B.
- **`status_histories` free-text reason (D11 deviation).** The roadmap/inventory language suggests the rejection reason lives in `status_histories`, but that schema is `{ entityType, entityId, from, to, actor }`. This change stores the reason on `verifications.reason` + the emitted event. If a later session extends `status_histories` with a reason column, the reject flow can forward it there without a behavioral change.
- **`duration` has no producer (D13).** The inventory expects experiences to copy `title/description/skills/duration` and stats to do `volunteerHours = duration`, but no schema has a duration field today. This change stores `duration` (default `0`) so the shape and the `$inc` are correct; a later session must add a source (e.g. a position `duration` field) to make `volunteerHours` nonzero.
- **Portfolio linkage (deferred).** Whether `volunteer_experiences` should ever appear in S13's portfolio flows is a P2 decision; this change keeps experiences independent of portfolio.
