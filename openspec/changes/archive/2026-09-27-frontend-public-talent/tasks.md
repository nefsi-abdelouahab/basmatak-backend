## 8. Implementation notes and deviations

- **Verification ran under a concurrent session.** `frontend-public-orgs` became active and began writing into the same `/frontend` tree mid-implementation (its in-flight `PublicOrgProfilePage` failed the type build on an undefined `orgDisplayCode`). Consequently:
  - `npm run build` passed with this change's routes compiled and listed (`/[locale]/talents`, `/[locale]/volunteers/[username]`) at the point before that code landed; the later full build failed **only** in the other session's file.
  - `npm run lint` and `npx tsc --noEmit` were run scoped to this change's files (clean); the only remaining `tsc` diagnostics are the pre-existing baseline in `src/lib/api/auth.test.ts`, `src/lib/api/portfolio.test.ts`, and `e2e/volunteer-credentials.spec.ts`.
  - `npm test` passed 430/430 across 54 files before the other session's test files landed.
  - `npx playwright test e2e/public-talent.spec.ts` passed 27/27 (viewport matrix 1440/1100/390 × en/ar) against a `next dev` server, because the `next start` harness needs the full production build the other session's code currently blocks.
- **2.1 media hook shape:** implemented `usePublicMediaQuery(mediaId)` (singular, one query per distinct id) rather than a batched `usePublicMediaQueries(mediaIds)`. `GET /media/:mediaId` is a per-id route, so per-id queries are what the endpoint shape allows; TanStack's per-key cache gives the same dedupe by id.
- **4.1 metadata:** the route `page.tsx` is a thin `setRequestLocale` wrapper with no `generateMetadata`, exactly mirroring the F5 `[idOrSlug]` route the task names as the model, because the page component is a client component that owns its own fetch.
- **Favorite-state reconcile (4.3):** F4's `useToggleTalentFavoriteMutation` is reused unchanged, and its `onSuccess` only invalidates `volunteer-home*`/`favorites` domains, so this session's own cards would keep a stale `aria-pressed`. Two narrow invalidators (`invalidatePublicTalentProfile`, `invalidatePublicTalentDirectory`) were added to the owned hook file rather than editing the shared hook.
- **Guest redirect path (4.3 / 5.2):** `getLoginHref` returns an already-localized `/{locale}/login?next=…`, and a locale-aware next-intl router prefixes the locale a second time (producing `/en/en/login`). This change navigates with `window.location.assign` so the path is exact. The latent double-prefix remains in the pre-existing F4/F5 call sites; their archived test only asserts `toContain('/en/login')`, which matches `/en/en/login` as a substring. **Left untouched as out of scope — worth a separate follow-up.**
