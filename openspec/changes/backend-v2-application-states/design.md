## Context

The v1 applications module (inventory §2.9) already stores an optional `message` on the schema (`applications.message`, `{ type: String, trim: true, maxlength: 2000 }`), but the apply route (`POST /opportunities/:id/positions/:pid/applications`) accepts **no body**, so the field is dead: it is never written, and every apply silently drops the applicant's cover note (RP §1.5#1, §2.4#6). The state machine registered in `ApplicationsModule.onModuleInit` is the v1 machine `pending → accepted|rejected|withdrawn`, `accepted → withdrawn`; there is no `under_review`, so the org's "Under review" tab (RP §2.4#1) has no state behind it and accept/reject only act on `pending`. The org reads applications only per-opportunity via `GET /opportunities/:opportunityId/applications`; the dashboard's cross-opportunity "Recent applications" list (RP §2.1#6, §2.4#3) has no aggregate endpoint.

Constraints carried in: the `StatusTransitionService.assert(entityType, entityId, from, to, actor, session?)` validates against the whitelist registered by the owning module and writes `status_histories` (`{ entityType, entityId, from, to, actor }` — no free-text column). The accept route is a multi-document Mongo transaction (`@InjectConnection().startSession()` + `withTransaction`, in-txn guarded seat update, participant insert, in-txn status history + in-app notification via `NOTIFICATIONS_REPOSITORY`, post-commit emit) — the F2/F4 pattern. Cursor pagination is the S1 convention (`common/pagination/*`, default 20 / max 50, newest-first on `_id`). The global `AppValidationPipe` is `whitelist + forbidNonWhitelisted + transform`. The seam convention lives in `src/common/seams/`: an interface + inert default, swapped by the owning session via Nest DI (`REGISTRATION_EXTRAS_SERVICE`, `PublishGateService`, `MediaOwnership`).

## Goals / Non-Goals

**Goals:**
- Apply accepts `{ message? }`, stores it, returns it in own-volunteer and org read payloads, and never lets it change after apply.
- `under_review` becomes a real application state: whitelist-paired transitions, an org-only `POST /applications/:applicationId/start-review` (`pending → under_review`), and status-aware accept/reject/withdraw valid from `pending` or `under_review`.
- The dedupe guarantee survives the new state: `under_review` stays "live" for the partial `(positionId, volunteerId)` unique index.
- `GET /organizations/me/applications` aggregate inbox across the org's opportunities with `?status=&opportunityId=&q=` + cursor pagination, plain projections, backed by a new `(organizationId, status)` index.
- The `ApplicationInboxJoiner` seam defined and inert; Session 17 fills the real name join without touching this module.

**Non-Goals:**
- Name/entity embeds of any kind (volunteer/org/opportunity/position display names) — Session 17 (`org-embed-labels`) owns them; this session only leaves the seam. Caller-name search in `?q=` is therefore deferred with the join.
- Audit-timeline exposure of application `status_histories` on a detail route (Session 18 activity / client-side rendering per RP §1.5#5).
- Messaging of any kind (decision 2, RP §1.5#7, §2.4#9).
- Changing the accept-withdraw transaction shapes themselves (seat/participant/notification logic) — this session only widens their allowed source status.
- `CursorPage` totals/`page`/`pages` — Session 2 (`pagination-totals`).
- Replacing the civic "APL-…" id rendering — client-side short-ObjectId (RP §2.4#11), no backend id.

## Decisions

**D1 — Apply body: a single optional `message`, immutable, already-readable.** Add `ApplyApplicationDto { message?: string }` (`@IsOptional() @IsString() @MaxLength(2000)`), pass it to `ApplicationsService.apply(account, opportunityId, positionId, dto?.message)` and write it in the `applicationModel.create` call (`message: trimmed ?? undefined` — the schema already trims and stores it). Immutability costs nothing: there is no PATCH for applications' envelope fields today, and we add none. Read exposure is free because the list/detail routes return whole documents; the spec asserts `message` appears in `/applications/me`, `GET /applications/:id` (volunteer and org), `GET /opportunities/:id/applications`, and the new inbox. The global pipe's `forbidNonWhitelisted` already rejects stray apply-body fields with `400 VALIDATION_ERROR`.

**D2 — Whitelist carries the full v2 application machine, additively.** Replace the registered pairs with: `pending → accepted | rejected | withdrawn | under_review`, `under_review → accepted | rejected | withdrawn`, and `accepted → withdrawn`. The registry is a `Set` keyed on `"from->to"`, and `register` adds without removing, so this is additive and idempotent on re-registration. `under_review → withdrawn` is included per the roadmap's stated machine — "`pending | under_review`, then `accepted | rejected | withdrawn`" — and the withdraw plain path widens to accept it (D5). No v1 pair is removed; all transitions go through `StatusTransitionService.assert`, preserving the `status_histories` audit trail.

**D3 — `start-review` is explicit, non-idempotent, org-owner 404.** `POST /applications/:applicationId/start-review`: resolve the owning org from the JWT (`organizations.userId → _id`, mirroring `requireOwnOrganization`); treat foreign orgs and volunteers as 404 (`APPLICATION_NOT_FOUND`). Then a status-scoped `findOneAndUpdate({ _id, status: 'pending' }, { $set: { status: 'under_review' } }, { new: true })` — matchedCount 0 → `409 INVALID_APPLICATION_STATUS` — followed by `assert({ entityType:'application', from:'pending', to:'under_review' })`. Non-idempotent by design: the roadmap says "`pending→under_review`, 409 if not pending", so an already-`under_review` call fails instead of silently no-op'ing (this differs deliberately from the submissions module's idempotent start-review, whose implicit inbox-open auto-start needs a no-op; applications has no such implicit path). The 409 taxonomy matches the existing reject/withdraw errors.

**D4 — Accept stays a transaction; its from-status widens.** The accept transaction body (seat guard, participant insert, in-txn history + notification, post-commit emit) is untouched. Two spots change, both status-scoped so the transaction stays race-safe against a concurrent `start-review` or other decision:
1. The application update guard `updateOne({ _id, status: 'pending' })` becomes `updateOne({ _id, status: currentStatus })` where `currentStatus` is the application's status read just before the transaction (`pending` or `under_review`); a concurrent flip makes `matchedCount === 0` → rollback with 409 `INVALID_APPLICATION_STATUS`.
2. The in-txn `assert` uses the same source: `from: currentStatus, to: 'accepted'` (registering both `pending → accepted` and `under_review → accepted` via D2). The application row is the source of truth for `currentStatus`; no extra read inside the transaction is needed (same posture as v1, which read status outside and guarded inside).

**D5 — Reject and withdraw widen to `pending | under_review`.** Reject already reads the application once (`requireById`), then `findOneAndUpdate({ _id, status: 'pending' }, { $set: { status:'rejected', reason } })`. It becomes status-scoped to the read status (`pending | under_review`) with the matching `assert` source. Withdraw's plain path (`findOneAndUpdate({ _id, status: 'pending' }, { $set: { status:'withdrawn' } })`) becomes `status: { $in: ['pending','under_review'] }` with a status-aware `assert`. The accepted (transactional) withdraw path is unchanged. Error messages update to reflect the allowed sources; codes stay `INVALID_APPLICATION_STATUS` / `409`.

**D6 — The dedupe index widens so `under_review` still counts as "live".** The partial unique `(positionId: 1, volunteerId: 1)` index currently filters on `status: { $in: ['pending','accepted'] }`. A row moved to `under_review` would silently drop out of that index and allow a second application for the same pair — wrong (the first is still live and the org is reviewing it). Widen the `partialFilterExpression` to `status: { $in: ['pending','under_review','accepted'] }`. Because Mongo cannot alter a partial filter in place, the migration recreates the index once (backfill is trivially safe — the filter only widens, so no historical row changes meaning). Also add `(organizationId: 1, status: 1)` (D7).

**D7 — New `(organizationId, status)` index for the aggregate inbox.** Applications carries `(opportunityId, status)` and `(volunteerId, status)` but nothing org-scoped; the inbox query `{ organizationId, status?, opportunityId? }` would otherwise scan. Add `ApplicationSchema.index({ organizationId: 1, status: 1 })` — additive, auto-built on boot (test rig + local dev), Atlas warm-up as usual. `(opportunityId, status)` serves the `?opportunityId=` variant; the `_id` sort keeps newest-first cursor pagination cheap.

**D8 — Aggregate inbox: service + DTO + controller, plain projections, `q` = opportunity/position title match.** `GET /organizations/me/applications` (root applications controller, organization role) with `OrganizationApplicationsQueryDto { opportunityId? (IsMongoId), status? (IsIn APPLICATION_STATUSES), q? (IsString, MaxLength 100), cursor?, limit? }`. The service resolves the org, builds `{ organizationId }` + optional `status`/`opportunityId`, and for `q` pre-resolves the org's own opportunities whose `title` (or embedded `positions.title`) matches a bounded `$regex`, collecting their ids into the application filter (`opportunityId: { $in: [...] }` combined with other filters) — no text index, bounded scan over the org's opportunity set, consistent with the F11 feed posture. Rows go through the seam (D9) last. Volunteer callers → 403 via the role guard. The roadmap's `&page=` notation maps to the repo's cursor convention (`cursor` + `limit`); numeric `page`/`total` arrive with `pagination-totals` in Session 2.

**D9 — `ApplicationInboxJoiner` seam follows the seam convention.** New `backend/src/common/seams/application-inbox-joiner.ts`: `APPLICATION_INBOX_JOINER` token, `ApplicationInboxRow` interface (the application document's plain fields the joiner may need — `_id`, `opportunityId`, `positionId`, `volunteerId`, `organizationId`, `status`, `message`, `reason`, timestamps), `ApplicationInboxJoiner.enrich(organizationId, rows): Promise<ApplicationInboxRow[]>` contract, and `InertApplicationInboxJoiner` returning the rows unchanged. Bind it in the global `CommonModule` (provider + export under the token) so the applications service injects it by token with zero module wiring. Session 17 overrides the token with the real name join (S1 convention, source-compatible). The inbox returns the plain rows today — the spec's "name-free while inert" claim is the acceptance test.

**D10 — Tests.** Unit (service-level, `startMemoryConnection` pattern): whitelist pairs admitted/rejected, `start-review` 404/409 semantics, accept/reject from `under_review` with correct single history row, withdraw from `under_review`, seam passthrough, oversized `message` rejected by DTO validation. E2E (`backend/test/applications.e2e-spec.ts` extends `describe` for the v2 surface): apply-with-message persists and is visible to volunteer and org reads; start-review → `under_review`; accept-from-under_review and reject-from-under_review each write exactly one history row and (accept) claim exactly one seat; repeated start-review → 409; aggregate inbox paginates across two opportunities, filters by `status`/`opportunityId`/`q`, and never leaks a second org's rows; volunteer → 403; foreign org start-review → 404; a stranger org's accept → 404; the wider dedupe index rejects a duplicate while an application is `under_review`.

## Risks / Trade-offs

- **Partial-index recreation touches a live production index.** The `partialFilterExpression` cannot be changed in place; the index must be dropped and rebuilt once. → The filter only widens (a superset of rows becomes unique-guarded), so the rebuild is safe; documented in this session's migration plan and run as part of deployment, not deferred to Session 21. Dev/test rigs rebuild via `autoIndex` on boot.
- **Race between `start-review` and `accept`/`reject`.** A decision read as `pending` that is concurrently flipped to `under_review` must not double-apply a transition. → Every write is status-scoped with a `matchedCount` guard and the in-txn `assert` re-checks the whitelist pair; a lost race rolls back / fails with `INVALID_APPLICATION_STATUS` (unchanged v1 posture, now for both source statuses).
- **`q` semantics are narrower than RP §2.4#2's "name/opportunity/position".** Names are not joinable without the S17 embeds. → This session implements opportunity/position-title search and explicitly leaves caller-name search to Session 17's joiner; the DTO contract already accepts `q`, so the later session can broaden the filter without an API change.
- **`under_review → withdrawn` inclusion is a reading of the roadmap's machine line.** If the owner intended a volunteer to be unable to retract once review begins, the pair can be dropped with one line. → Flagged as an Open Question; the spec/tasks already document the chosen behavior and the 409 path is identical either way.
- **Route-order collisions.** `/organizations/me/applications` (applications controller, 3 segments) vs `/organizations/:slug` (organizations controller, 2 segments) and `/opportunities/:id/applications` — distinct shapes, no Express swallowing. → Verified against both controllers; the e2e asserts the inbox responds under the global `/api/v1` prefix and that org `GET /organizations/me` still works.

## Migration Plan

- **Schema/collection:** no data migration — `message` already exists and is optional; the status field defaults to `pending`, so existing rows keep a legal enum value; the new `under_review` value needs no backfill.
- **Indexes:** add `(organizationId, status)` (auto on boot); recreate the partial unique `(positionId, volunteerId)` index with the widened `partialFilterExpression` including `under_review` (documented one-time production step for Atlas; auto in dev/test).
- **Runtime:** whitelist re-registration and new routes are additive; the old (v1) machine pairs remain allowed, so no in-flight application regresses.
- **Rollback:** revert the change commit. The widened index would still be a superset for a short window (harmless — it only blocks what the widened state also blocks); re-running the old code with the new index is safe. No data cleanup required.

## Open Questions

- **Withdraw during review (D2/roadmap reading).** The roadmap's machine ("`pending | under_review`, then `accepted | rejected | withdrawn`") implies `under_review → withdrawn`; this session implements it. If the owner wants review to lock the applicant out, drop the pair and the withdraw branch — verified with the E2E.
- **`?q=` scope.** Opportunity/position-title search only until Session 17 proves name joins; the `q` contract is final either way.
- **`page` notation.** The roadmap's `&page=` is served by the repo's `cursor`/`limit` convention; numeric `page`/`pages`/`total` arrive with Session 2 `pagination-totals`. No blocking question.
