## Context

The core loop is open at the reporting stage. S7's accept transaction seeds a `task_participants` row with `{ opportunityId, positionId, applicationId, organizationId, volunteerId, status }` and the embedded `position` sub-document in `opportunities` carries the task's `title`/`description`. S8's media module owns `MediaOwnership` (global `@Injectable`), which exposes `assertFor(mediaId, actorId, purpose)` — existence, ownership (404 `MEDIA_NOT_FOUND` for absent/foreign), and purpose (409 `MEDIA_PURPOSE_MISMATCH`) — with `submission_evidence` already an allowed `MediaPurpose`. S9's `NotificationsEventHandlers` already forwards-registers `submission.submitted` (reads `payload.submission.organizationId` → notifies the org account), so this session only emits. The S1 `StatusTransitionRegistry.register(entityType, pairs)` pattern is proven by S6 (`opportunity`) and S7 (`task_participant`) module `onModuleInit` hooks; `StatusTransitionService.assert` validates + writes `status_histories`.

There is no `submissions` collection, no module, and none of the eight §2.12 routes. Media metadata lives in `media` rows (`type: file|l link`, `mimeType`, `confirmedAt`, `deletedAt`); videos are `type=link` (host allowlist), images/pdfs are `type=file`. Those media rows are what the consent rule and the "evidence per deliverable" rule read.

Constraints carried into this design: NestJS 10 + TS strict, Mongo ObjectId ids, `/api/v1` prefix, `{ statusCode, code, message, details? }` errors with UPPER_SNAKE codes, cursor pagination (default 20 / max 50) via `common/pagination/*`, class-validator whitelist + forbidNonWhitelisted, and the §6 rule that the only entity a caller may not read is treated as not-found (404 for foreign ownership). One session = one OpenSpec change; this change is shared with Part B, so the whitelist carries the full machine now and Part B only writes `approved|rejected`.

## Goals / Non-Goals

**Goals:**
- A `submissions` module (`backend/src/submissions/`) with a `submissions` collection: `participantId` (unique — one submission per participation, reused on resubmission), denormalized `volunteerId`/`opportunityId`/`positionId`/`organizationId`, `deliverables` (position-derived descriptor snapshots), `description`, `consentConfirmed` (Boolean, default `false`), `evidence` (array of `{ mediaId }`), `status` (`draft` default), S1 base options and the §3 indexes `(opportunityId, status)` + `(volunteerId, status)`.
- The eight §2.12 routes: create (409 on second), patch (draft edits; rejected→draft), submit (draft→submitted with description + evidence-per-deliverable + consent rule), `me`, detail (owner/org, includes media metadata), org inbox (`?status=&opportunityId=`), and `start-review` (submitted→under_review).
- `submission` whitelist registered at bootstrap (full machine, so Part B needs no re-registration) and `submission.submitted` emitted after each successful submit exactly once via the S1 EventEmitter bus.
- E2E in `backend/test/submissions.e2e-spec.ts` plus unit coverage for submit validation and the rejected→draft round-trip.

**Non-Goals:**
- Verify/reject routes, the `verifications` collection, experiences, portfolio, reviews, and stats — all Part B (S11/S13).
- Changing S9's already-registered handler or adding a new notification handler; changing S7/S8 module code beyond reading their models.
- Any new package, env var, or route beyond the eight; no changes to `opportunities`/`applications`/`participations` collections beyond reads.

## Decisions

**D1 — Module layout.** New `backend/src/submissions/`:
- `schemas/submission.schema.ts` — `SubmissionsCollection = 'submissions'`, `SUBMISSION_STATUSES = ['draft','submitted','under_review','approved','rejected']`, fields per the spec, `evidence: [{ mediaId: ObjectId }]`, `deliverables: [{ title, description }]`, `consentConfirmed` default `false`, `status` default `draft`, `createSchema` base options (timestamps, `versionKey:false`, ObjectId→string `toJSON`). Indexes: unique `participantId`, `(opportunityId, status)`, `(volunteerId, status)`.
- `submissions.service.ts` — `createForParticipation`, `updateDraft`, `submit`, `listMine`, `getDetail`, `listForOrganization`, `startReview`; the only file that calls `MediaOwnership`, `StatusTransitionService`, and `EventEmitter2`.
- `submissions.controller.ts` + `dto/submission.dto.ts` — the eight routes, `Auth` guards, role guards: volunteer routes use the volunteer role (create/patch/submit/me/detail) and org routes use the organization role (inbox/start-review/detail). All callers come from the JWT `sub`.
- `submissions.module.ts` — `MongooseModule.forFeature` for `SubmissionsCollection`, re-registers `OpportunitiesCollection` + `TaskParticipantsCollection` (precedent: notifications module re-registers foreign models for read-only lookup), and implements `OnModuleInit` registering the `submission` whitelist.

**D2 — Create derives the draft from the participant + its position.** `POST /participations/:participationId/submissions`: load the `task_participants` row by `_id` scoped to caller `volunteerId` (absent/foreign → 404, matching S7's `requireOwned*` pattern), then load the opportunity and its embedded `positions` sub-document by `participantId` → `positionId`. `deliverables` is a snapshot `[{ title, description }]` copied from that position sub-document — a descriptor-per-position array so the evidence-per-deliverable rule is checkable against a stable, immutable snapshot even if the org later edits the opportunity. `volunteerId`/`opportunityId`/`positionId`/`organizationId` come from the participant row (denormalized so the inbox/detail/notification never need joins). Insert competes against the unique `participantId` index; a duplicate surfaces `E11000` → `409 SUBMISSION_ALREADY_EXISTS`. Alternative considered — letting the volunteer author `deliverables` freely — rejected: the inventory pins deliverables to the position's expected outputs and a free-typed list would let volunteers change the contract on resubmission.

**D3 — Edit semantics (rejected→draft, one record, unlimited resubmission).** `PATCH /submissions/:submissionId` accepts `{ description?, evidence?, consentConfirmed? }`. Owner check first (foreign → 404). If `status === 'rejected'`, transition `rejected → draft` via `StatusTransitionService.assert` and then apply the edit; if `status === 'draft'`, apply directly; any other status (`submitted`/`under_review`/`approved`) → 409 `INVALID_STATUS_TRANSITION`. Every evidence `mediaId` in the incoming array is validated through `MediaOwnership.assertFor(mediaId, volunteerId, 'submission_evidence')` before the update is written, so the whole patch is atomic as a single `findOneAndUpdate` after validation (no partial state). This mirrors the §5 machine (`rejected → draft → submitted again`, unlimited) and decision 2 / roadmap; the same record is always reused.

**D4 — Submit is validate-first, then transition, then emit.** `POST /submissions/:submissionId/submit`: owner check (404 for foreign). Validation order, each a `400` business error with no transition written:
1. `description` is non-empty.
2. Every `deliverables` entry is covered by at least one `evidence` mediaId (allow one evidence to satisfy exactly one descriptor — matching the inventory's "at least one evidence per deliverable"). No evidence at all → 400 `EVIDENCE_REQUIRED`; any unevidenced descriptor → 400 `EVIDENCE_REQUIRED`.
3. Any evidence media whose row is `type=link` (video) or `type=file` with an `image/*` mimeType requires `consentConfirmed === true` (decision 6). Missing → 400 `CONSENT_REQUIRED`. PDF-only evidence never triggers the rule.
   The media rows are fetched via `MediaOwnership.assertFor` per evidence id (this doubles as the existence/ownership/purpose gate on submit, matching the patch path).
Then `StatusTransitionService.assert({ entityType:'submission', entityId, from:'draft', to:'submitted', actor })` writes the history, the row is updated to `submitted`, and only after both succeed `this.events.emit(DomainEvents.SubmissionSubmitted, { submission: updated })` — payload shape matching S9's handler (`payload.submission.organizationId`). The E2E routes list the emitted payload through the injected `EventEmitter2` (precedent S9 §5.1).

**D5 — Registration timing and full-machine whitelist.** `SubmissionsModule.onModuleInit` calls `registry.register('submission', [['draft','submitted'],['submitted','under_review'],['under_review','approved'],['under_review','rejected'],['rejected','draft']])` — identical to the S6/S7 pattern. The whitelist intentionally carries `approved|rejected` now so Part B's verify/reject transactions only call `assert` and never touch registration; this session implements no `approved|rejected` write path. `StatusTransitionService.assert` rejects anything unlisted (`INVALID_STATUS_TRANSITION`, 409) and writes nothing.

**D6 — Detail and inbox resolve ownership without joins.** `GET /submissions/:submissionId` loads the row and returns it with evidence media metadata; access: caller's `volunteerId` matches the row, or an org account whose own organization (`organizations.userId → organizations._id`) equals the row's `organizationId`. Otherwise 404 (non-owner read = not-found, §6). The org inbox `GET /organizations/me/submissions` resolves the org id from the JWT account once, then queries `{ organizationId, ...(status), ...(opportunityId) }` with the §3 `(opportunityId, status)` index; foreign org rows are structurally unreachable. Volunteer calling the inbox → 403.

**D7 — Cursor pagination reuses the S1 helpers.** `me` and inbox use the existing `common/pagination/*` encode/decode with `limit` default 20 / max 50, newest-first (`_id` descending), cursor on `_id`. The DTOs are class-validator whitelist + forbidNonWhitelisted.

**D8 — Automatic start-review on inbox open is optional, so the explicit route is the contract.** `POST /submissions/:submissionId/start-review` is implemented unconditionally (owning org → 404 for others; any non-`submitted` status → 409 `INVALID_STATUS_TRANSITION`; else `submitted → under_review` through `assert`). Auto-start on first inbox open is left to the frontend to invoke (the road map lists it as "may be implicit"); because `under_review` is in the whitelist, a repeated auto-start call is idempotent (already-`under_review` → assert's `INVALID_STATUS_TRANSITION` would fire, so the service treats `under_review` target state as success — no second history row). Decision: keep the service semantics "transition TO under_review" and treat an already-`under_review` row as a no-op success for the implicit path.

## Risks / Trade-offs

- **Unique-index-driven 409 depends on catching `E11000`.** If the unique `participantId` index were ever dropped, a second create would silently write a second row. → Schema declares the index; the E2E seeds a duplicate-create case against the running rig, and the service also does an explicit pre-check `findOne({ participantId })` before insert (belt-and-braces; the E11000 catch remains the authoritative race guard).
- **Editing the opportunity after a draft is created no longer re-derives `deliverables`.** That is intentional (stable snapshot for evidence coverage), but an org editing position titles mid-draft could make the snapshot diverge from the current position. → The snapshot is end-user-facing text; the slug/title divergence is cosmetic and Part B's verify notes can reference it. Documented trade-off, not a correctness risk.
- **Emit-after-commit is not transactional with the submit.** A crash between the transition write and the bus emit loses the notification (the row is `submitted`, the org gets no nudge). → Same posture as S7's post-commit conveniences; the row itself is the source of truth and the inbox still lists the submission. Not retried in this session (no queue, per the roadmap's no-queues constraint).
- **Media rows are read (not transactionally updated) for consent/ownership.** A media row deleted between validate and save → the submission references deleted media. → `assertFor` filters `deletedAt: { $exists: false }`; Part B's verify transaction will re-check liveness before approving. Acceptable for MVP.
- **Module ordering in `app.module.ts` must stay additive.** Sibling archives warn against reordering existing imports. → Append `SubmissionsModule` to the imports array; the full build/e2e gate plus the `GET /organizations/me/submissions` (org-owned) vs `GET /participations/:id/submissions` (volunteer) route split have no path collisions with existing controllers.

## Migration Plan

New `submissions` collection only. Indexes (unique `participantId`, `(opportunityId, status)`, `(volunteerId, status)`) build on first boot; `autoIndex` is on for the test rig and local dev, Atlas warm-up like every prior session. `app.module.ts` gets one additive import; no existing collection, env var, or route changes. Rollback: revert this session's single commit; nothing else depends on the submissions module yet (the S9 handler is a no-op until `submission.submitted` is emitted). Part B extends the same collection + whitelist via MODIFIED deltas on the `submissions` capability.

## Open Questions

- **Auto-start UX ownership.** Whether the frontend triggers `start-review` explicitly or the inbox auto-starts on open is a UI decision; the backend supports both (D8). No blocking question.
- **Deliverable descriptor shape.** The snapshot is `[{ title, description }]` per position (D2). If a future session adds a richer `deliverables` structure to positions, this module would read it through the same snapshot seam — noted for Part B.
