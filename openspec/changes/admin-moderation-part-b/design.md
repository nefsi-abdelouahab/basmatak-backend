## Decisions

**D1 — Part B reuses the Part A module layout: controllers + services in `admin.module.ts`, one mongodb `reports` module.** Five new controllers are added to `backend/src/admin/` (`AdminOpportunitiesController`, `AdminReviewsController`, `AdminReportsController`, `AdminAuditController`, `AdminSettingsController`), each `@Controller('admin/...')` + `@Roles('admin')` exactly like Part A's, each backed by a small service (or reusing existing ones) so the module grows by composition. The new `backend/src/reports/` module (`reports.module.ts`) owns `report.schema.ts`, a `ReportsService` (create + paginated list + resolve), and a `ReportsController` exposing only `POST /reports` (Auth, any log-in role). Admin list/resolve live in `AdminModule` (per §2.19/§2.20 ownership), so `AdminModule` imports the reports model via `MongooseModule.forFeature` (a `ReportsModule` export of the model is the alternative; decide by the existing Mongoose re-registration precedent — Part A re-registers foreign models directly in the admin module, so Part B does the same).
- `admin.module.ts` `onModuleInit` additionally registers the `report` whitelist (`open → in_review`, `open → resolved`, `open → dismissed`, `in_review → resolved`, `in_review → dismissed`) — the opportunity whitelist already covers the admin force-close pairs (`published|cancelled` from Part A's S6, unchanged; no re-registration needed).

**D2 — `GET /admin/opportunities` is a paginated, newest-first projection with NO extra indexes.** Reuses the Part A D3 cursor convention: `find({})`, sort `_id: -1`, `-passwordHash` not applicable (no user fields), select a moderate admin shape (id, title, slug, organizationId, status, startDate… via `.select`), normalize `limit` via `normalizeLimit` (default 20, max 50), encode the last `_id` as cursor. Read-only; no new indexes (inventory §3 already covers `(organizationId, status)` and `(status, startDate)`; a global newest-first sort rides `_id`).
- DTO: reuse a generic `CursorQueryDto`-style shape (the `admin-query.dto.ts` pattern): optional `cursor`/`limit` strings.

**D3 — `PATCH /admin/opportunities/:opportunityId/status` mirrors Part A D5's guard-proof loop on the *opportunity* entity.** Load opportunity by `opportunityId` → `404 OPPORTUNITY_NOT_FOUND` when absent (invalid ObjectId → the global CastError → 400 filter). Compare the requested `status` (`closed` | `cancelled`, DTO `@IsIn`) with the current: equal → `409 INVALID_STATUS_TRANSITION` (no-op). Else `StatusTransitionService.assert({ entityType: 'opportunity', entityId, from: current, to: requested, actor: admin userId })` — the existing whitelist already permits `published → closed|cancelled` and `in_progress → closed|cancelled`. Then update the doc `{ status: requested }`. A draft opportunity (no legal transition) fails at the whitelist with `409` — correct, admins force-close only live opportunities. E2E: force-close an `in_progress` opportunity and assert `status === 'closed'` and a `status_histories` row exists.

**D4 — Review hiding is a schema field addition + a reliability-query exclusion, both additive-only.** `ReviewSchema` grows `status: { type: String, enum: ['visible','hidden'], default: 'visible' }` (additive; the three existing indexes are kept as-is, and `status` is intentionally NOT indexed — the admin hide mutation is by `_id`, and the reliability read filters by `organizationId: { $in: [...] }`, `status`). `PATCH /admin/reviews/:reviewId/hide` (`@Roles('admin')`, audited): load → `404 REVIEW_NOT_FOUND` when absent; no-op (`status === 'hidden'`) → `409`? — Part A's D5 convention rejects no-op status sets with `409`; this mutation is not a `StatusTransitionService` transition (review status is a moderation flag, not a lifecycle machine), so the route applies the no-op 409 inline for symmetry and spec clarity. Update `{ status: 'hidden' }`.
- `ReliabilityService.computeFor` appends `.where('status').ne('hidden')` to BOTH the org-review query and the platform-review query used for `anomalyFlag`, and `deriveMetrics`/`anomalyFlag` stay pure (the filter happens at query time, keeping the unit-testable signature unchanged). This is the ONLY edit to `src/trust/reliability.service.ts` (S13 uncommitted work — touch nothing else there).

**D5 — The reports module owns schema, indexes, and the state machine registration.** `report.schema.ts`: `{ reporterId (ObjectId, required), targetType (enum from the DTO — see D6, required), targetId (ObjectId, required), reason (String required, trimmed), description (String optional), status (enum open|in_review|resolved|dismissed, default 'open'), resolution (String optional) }` + timestamps via `createSchema`. Indexes per §3: `(status, createdAt)` and `(targetType, targetId)`. `ReportsModule.onModuleInit` registers the `report` whitelist in the registry (`open → in_review | resolved | dismissed`, `in_review → resolved | dismissed`) so `StatusTransitionService.assert` validates every resolution. No `targetType`/`targetId` existence cross-check (reports can target soft-deleted entities; the ids are stored opaquely) — documented as accepted scope.

**D6 — `POST /reports` is open to any logged-in role; list/resolve are admin.** `POST /reports` (`@Controller('reports')`, no `@Roles`, Auth via the global JWT guard): DTO `{ targetType (IsIn(['opportunity','user','organization','review','submission'])), targetId (IsMongoId), reason (IsString, IsNotEmpty, MaxLength 2000), description (IsOptional, MaxLength 4000) }`, stores `reporterId = account.sub`, status default `open`. Returns the row (201). `GET /admin/reports?status=` (optional `@IsIn(['open','in_review','resolved','dismissed'])`) — cursor paginated newest-first; `PATCH /admin/reports/:reportId` with `{ status (required IsIn), resolution? (optional) }`: load → 404 `REPORT_NOT_FOUND`; `StatusTransitionService.assert({ entityType: 'report', from: current, to: requested, actor })` (open/in_review → the whitelist rejects illegal or no-op sets with `409`); set `{ status, resolution? }`. Every write audited by the interceptor (admin routes).

**D7 — Audit-log browsing is a read-only projection over the S1 model, filters map to existing indexes.** `GET /admin/audit-logs?actor=&entity=&date=` (all optional strings): `actor` filters `actorId` (ObjectId-validated → CastError → 400 on malformed), `entity` is the inventory's `(entityType, entityId)` pair — accept as `entityType` + `entityId` query params (`?entityType=&entityId=`) for spec-level clarity and map to the `(entityType, entityId)` index; `date` is a single date bound `createdAt: { $lte: endOfDay }` (the `createdAt` index). Page newest-first by `_id`. Read-only, no writes, no schema/index changes (S1 already defines them); the interceptor does not audit GETs, so no recursion concern.

**D8 — Settings admin reuses `SettingsService`; key validation is whitelist-based; writes refresh the cache.** `GET /admin/settings` lists all `system_settings` rows (plain `find({})`, newest-first optional — list-all is fine at MVP scale; no pagination per inventory note "list all system_settings rows"). `PUT /admin/settings/:key` validates `key` against the known set `['publishGate.maxPendingOpportunities']` (DTO/route check: unknown key → `400 UNKNOWN_SETTING_KEY`), `value` is a JSON body value; calls `SettingsService.set(key, value)`, which upserts AND refreshes the per-key cache — so a subsequent `publishGate.maxPendingOpportunities` read (S13 gate) reflects the new threshold immediately. Returns the stored setting, `@Roles('admin')`, audited. This replaces the S1 "no admin settings controller" state (system-settings spec MODIFIED).

**D9 — Admin identity for tests (Part A D9 pattern).** No register path for role `admin` and no `seed:admin` yet (Session 17): the E2E builds the admin via `UsersService.create({ email, passwordHash, role: 'admin' })`, then obtains a token via `POST /auth/login`. Login is throttled → ONE shared admin token created in the suite's `beforeAll`, reused across tests, and `THROTTLE_LIMIT=100000` set in the app-creating helper (same helper pattern as Part A). Non-admin accounts (volunteer/organization) prove `403` on every new admin route.

**D10 — Wiring is append-only.** `ReportsModule` appended to `app.module.ts` imports; admin controllers appended to `AdminModule`; `MongooseModule.forFeature` entries added for `reviews`, `reports`, `audit_logs`, `system_settings` (opportunities already present). Route-order note: `AdminReviewsController`, `AdminReportsController`, `AdminAuditController`, `AdminSettingsController`, `AdminOpportunitiesController` are all distinct literal prefixes under `/admin` — no shadowing exists (verified: no `/admin/:param` catch-all route is declared).

## Risks / Trade-offs

- **`PUT /admin/settings/:key` accepts arbitrary JSON values.** → Key whitelist limits which keys exist; per-key value shape (e.g. number for the gate threshold) is asserted by the controller (validate `value` is a finite number for known numeric keys), preventing garbage from breaking the S13 gate. Unknown keys rejected `400`.
- **Review-hide no-op is a manual 409 rather than the transition service.** → The review status is a moderation flag, not part of the `status-transitions` `status_histories` machine; writing a history row for flag sets would pollute `status_histories` with non-lifecycle data. The 409 symmetry is asserted inline and unit-tested; documented in the reviews spec so the behavior is contractual.
- **Reports omit cross-entity existence validation.** → A report may target a soft-deleted (`status: deleted` / `hidden`) entity whose row was removed; an existence probe would create false negatives and extra reads. Target ids are stored opaquely; the community's `targetType`+`targetId` pair remains queryable. Accepted scope.
- **Reliability exclusion is query-time, not schema-level.** → Hidden reviews never enter the org metrics or the platform average because both read queries filter `status != 'hidden'`; the pure `deriveMetrics`/`anomalyFlag` signatures are unchanged so S13's unit tests still compile. If a future consumer queries reviews directly it owns its own filtering.
- **Audit-logs `date` filter is a single end-of-day bound.** → Inventory says `createdAt range`; implemented as `$lte` end-of-day (matches "how recent" moderator intents). If a from/to range is wanted later it's a additive DTO change, no schema impact.

## Migration Plan

No new env vars, packages, or pre-existing data migrations.
1. Create `backend/src/reports/` (schema, service, controller, module) and append `ReportsModule` to `app.module.ts`.
2. Add the five admin controllers/services to `admin.module.ts` + the four `forFeature` model registrations (`reviews`, `reports`, `audit_logs`, `system_settings`); register the `report` whitelist in `onModuleInit`.
3. Add `status` to `review.schema.ts` (additive, default `visible`); constrain the `ReliabilityService` read queries (D4).
4. Write unit + E2E tests; run the isolated e2e pattern `npm run test:e2e -- --forceExit --runInBand --no-cache --testPathPattern=admin-part-b`.
Backward compatibility: all changes are additive (new fields defaulted, new routes, new module); existing helpers/references keep working. Rollback: revert the commit — `Review.status` defaults to `visible`, hidden reviews are only excluded while the filter is present, and new tables are empty until used.
